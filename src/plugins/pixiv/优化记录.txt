# pixiv 插件优化记录（请先读这一份）

这次改动的四个文件：__init__.py、url.py、constant.py、utils.py。
目标按你的要求分三点：**更易读**、**更省算力**、**记录为什么改**。
下面每一条都写成「原来怎样 → 现在怎样 → 为什么」，最后一节是通用的写代码注意事项。

---

## 一、__init__.py（插件入口 / 流程编排）

### 1. 删掉 8 个没用到的 import
原来 import 了 requests、on_command、Message、ArgPlainText、Arg、CommandArg、
PrivateMessageEvent、T_State，但这些名字在整个文件里**只出现在 import 那一行**。
- 为什么：没用到的导入会让人以为"这里有相关逻辑"，读代码时要额外确认一遍；
  其中 requests 还是同步库，混在异步项目里会误导后来者。
- 怎么自查：对每个 import 名字在文件里搜一遍，只命中 import 行就是死导入。
  编辑器里一般会灰色显示，别习惯性忽略。

### 2. 把“解析用户输入”抽成三个小函数
原来 handler 里前 20 行全在做字符串切割，真正的业务流程被淹没。
现在拆成：

    _parse_count(cmd) -> int      # “来3张白丝涩图” -> 3
    _parse_tag(cmd)   -> str      # “来3张白丝涩图” -> “白丝”
    _session_id(event)-> str      # 群聊取群号，私聊取 QQ 号

- 为什么：一个函数只做一件事。解析规则以后要改（比如允许“来三张”），
  直接定位到 _parse_count，不用在 100 行的 handler 里翻。
- 顺带修掉一个隐患：原来群聊/私聊取 id 的那行
    id_ = str(event.group_id) if isinstance(...) else event.get_user_id()
  在同一个文件里写了两遍（发图一处、r18 开关一处）。两处一旦改得不一致，
  就会出现“在群里开了 r18，发图时却读不到”这种诡异 bug。现在只有一份实现。

### 3. 配置读写改用 utils.get_session / set_r18
原来每个用到配置的地方都要写一遍：

    if id_ not in customer_api.keys():
        customer_api[f"{id_}"] = {}
    api = customer_api[f"{id_}"].get("url", "lolicon API")

- 现在：session = get_session(session_id) 一行，缺失的键自动补默认值并落盘。
- 为什么：**默认值只应该存在一个地方**。原来 “lolicon API” 这个默认字符串
  在 __init__.py 里以字面量出现，一旦改名就要全文搜索替换，漏一处就行为不一致。
  现在默认值定义在 url.DEFAULT_API_NAME，__init__.py 引用常量而不是抄字符串。

### 4. 修掉“图片和链接会配错”的真 bug（重要）
原来的代码是：

    image_list = [image for image in image_list if image]   # 先丢掉下载失败的
    new_list = [await make_new_image(image_list[i]) ...]
    data = [dict(d, **{'image': i}) for i, d in zip(new_list, data)]  # 再和元数据 zip

问题：假设请求了 3 张，第 2 张下载失败。
- image_list 变成 [图1, 图3]，data 还是 [图1信息, 图2信息, 图3信息]。
- zip 之后：图3 配上了“图2的 pixiv_id 和链接”。
- 用户看到的卡片里，**图和它下面标的链接根本不是同一张**。

现在改成先配对、再过滤：

    downloaded = [(info, raw) for info, raw in zip(images, raw_list) if raw]

- 为什么：**只要两个列表有“按下标对应”的关系，任何过滤都必须成对进行。**
  先 filter 其中一个再 zip，是这类错位 bug 的经典来源。
  用顺序敏感的数据时，问自己一句：“我丢掉元素后，另一个列表的下标还对得上吗？”

### 5. 合成幻影坦克改用 asyncio.to_thread 逐张做
原来 await make_new_image(...)（当时它是 async 函数）。
现在 make_new_image 是**同步**的 numpy/Pillow 计算，改为：

    mirage = await asyncio.to_thread(make_new_image, raw)

- 为什么：同步的 CPU 计算直接写在 async 函数里，会把整个事件循环卡住
  （合成一张 2200×2200 要几百毫秒，期间 bot 收不到任何消息）。
  丢进线程池后事件循环照常转，同时是**逐张**处理，内存里只有一张原图+一张输出图。
  如果改成 asyncio.gather 全部一起做，10 张图会同时占用几个 GB。

### 6. 异常日志改成 logger.exception
原来 logger.error("出现错误：" + str(e))，现在 logger.exception("涩图流程出错")。
- 为什么：str(e) 只有一个光秃秃的消息，**没有堆栈**。
  线上只看到“出现错误：'NoneType' object is not iterable”时，
  根本不知道是 url.py 抛的还是 constant.py 抛的。
  logger.exception 只在 except 块里用，会自动带上完整 traceback。

### 7. r18 开关去掉了重复的 save()
原来开/关各写一遍 customer_api[...]["r18"] = True; save()。
现在 set_session_r18(session_id, True) 一步搞定，且内部保证改完立即落盘。
- 为什么：**“修改内存里的配置”和“写磁盘”这两件事必须绑在一起做。**
  分开写就一定会有人忘掉 save()，表现为“重启后设置丢失”。

## 二、url.py（图源 API 封装）

### 1. 把“请求参数”和“用户看到的文案”拆开
原实现只有一个 tag 字符串，一边拼成 &tag=白丝|萝莉，
一边又靠 tag[5:] 这种魔术切片把 &tag= 前缀切掉给用户看。
结果“没有找到【xx】”那里忘了切，会显示成 没有找到【&tag=白丝】。

现在 _parse_tag() 直接返回两个值：

    请求参数 "&tag=白丝|萝莉"   展示文案 "白丝|萝莉"

- 为什么：**同一个数据要同时满足两种用途时，别硬塞进一个变量。**
  拼接格式一变，切片的长度就全错了，而且这类 bug 不会报错，只会默默显示错内容。

### 2. 文案生成收敛到一个模板
原来 if/elif/else 三个分支里，“初号姬为你准备了…”这个句子被抄了四遍。
现在 _build_notice() 用模板拼，返回 (文案, 真正请求的张数)。
- 为什么：重复的字符串就是重复的 bug 修复点。改一次称呼要改四个地方，必然漏一个。

### 3. 失败时返回空列表，绝不返回 None
原来 HTTP 非 200 时 image_list = None，调用方紧接着
[i['url'] for i in data]，直接抛
TypeError: 'NoneType' object is not iterable ——
真正的错误信息“连接出错了...”被完全盖掉。

现在 lolicon() 的返回值约定是：

    成功 -> (文案, [{"pixiv_id": int, "url": str, "r18": bool}, ...])
    失败 -> (文案, [])

- 为什么：**函数的每种返回路径都应该保持同一种类型。**
  返回 None 把“判断有没有值”的责任推给了每个调用方，只要有一个调用方忘了判空，
  就会在离错误很远的地方炸掉，排查成本极高。返回空列表则天然安全，
  调用方一句 if not images 就能收口。

### 4. 网络请求走 utils/net.get（带重试 + 超时）
图源域名（api.lolicon.app / i.pixiv.re）会偶发 DNS 抖动，
报错形如 [Errno -2] Name or service not known / [Errno 11001] getaddrinfo failed。
utils/net.py 的 get() 默认重试 3 次、超时 20 秒。
- 为什么：**不要用裸 httpx.get()。** 一次网络抖动就让用户看到“出现错误”，
  而重试一次的成本几乎为零。重试要有个上限，否则域名真挂时会把请求全堆住。

## 三、constant.py（幻影坦克像素运算）

### 1. 全部改成 float32，别用 float64
2200×2200×3 的 float64 数组一个约 116MB，这个函数同时会有六七个这样的中间数组。
- 效果：内存和逐元素运算都减半。最终产物是 8bit PNG，
  float32 有 7 位有效数字，远远够用。
- 为什么：**图像像素运算一律用 float32。** 用 float64 是拿“根本没用的精度”
  去换内存和速度。只有做数值累加（如求和、均值）时才需要考虑 float64。

### 2. 逐通道下标运算改成广播
原实现：

    gray = r * 0.334 + g * 0.333 + b * 0.333
    pix *= ratio
    pix[:, :, 0] += gray * (1 - ratio)
    pix[:, :, 1] += ...
    pix[:, :, 2] += ...

同一块大数组被完整遍历了 4 遍。现在：

    gray = (pix @ _LUMA_RGB)[:, :, None]   # 一次矩阵乘法
    pix *= ratio
    pix += gray * (1 - ratio)              # 一次广播，三个通道同时完成

- 为什么：numpy 里能写成整体数组运算的，就不要写循环/逐通道。
  [:, :, None] 是广播的关键——它把 (H, W) 的灰度图变成 (H, W, 1)，
  再和 (H, W, 3) 相加时自动在三个通道上复制。

### 3. 只算一次灰度（核心公式的简化）
alpha 的三个通道数值完全相同，原实现却先把结果写回 d 的三个通道（多两遍全图拷贝），
再另外采样求 alpha。现在直接 d_gray = (d @ _LUMA_ALPHA)[:, :, None]。
- 为什么：**动手优化前先看一遍中间结果有没有冗余。**
  这里“三个通道一样”是数学事实，利用它就能省掉两遍全图遍历。

### 4. 删掉恒为空操作的画布拷贝
原 resize 之后又做了“各自 Image.new 一张 max 尺寸画布，再 paste 居中”。
但 _w_img 的尺寸既然由 _b_img.size 决定，两张图必然一样大，
width == w_width、height == b_height、粘贴偏移恒为 (0, 0)。
- 效果：2200×2200 的图每次少分配约 14MB 并少拷一遍，这个函数里省了两次。
- 为什么：**看到有偏移量的粘贴/画布，先算一下偏移量是不是常数 0。**
  很多“历史遗留的居中逻辑”在尺寸统一之后已经变成纯开销。

### 5. 用 lru_cache 缓存字体
原来每合成一张图都重新 ImageFont.truetype(...) 读一遍 ttf。
现在 @lru_cache(maxsize=8)，同一个字号整个进程只加载一次。
- 为什么：**参数少、返回值可复用、调用频繁的函数，就考虑缓存。**
  字体文件解析是典型的“慢但结果不变”。lru_cache 记得给 maxsize，
  无界限的缓存会一直吃内存。

### 6. 用 draw.textlength 量文字宽度
原来用 len(word) * font_size 估算宽度，只对等宽的中文大致成立。
现在 draw.textlength(word, font=font) 返回字体度量下的真实宽度。
- 为什么：**别用字符数近似排版宽度。** 中英文混排、标点、比例字体全会算错。

### 7. 删掉 gray_car（死代码）
全项目搜索确认零引用。
- 为什么：**没人调用的函数不是“资产”，是负债。**
  它会被搜索命中、被误认为可用、被复制粘贴，还会让你以为有人在维护它。
  git 里随时能找回，删掉不可惜。

### 8. 删掉“传 URL 自己去下载”的分支
原来 make_new_image 接受 URL 字符串并自行下载，为此整个文件全是 async，
resize、合成、字体全都被迫挂上 async。
现在只接受 bytes / BytesIO / Path，纯同步。
- 为什么：**不要让一个函数既做 I/O 又做计算。**
  混在一起之后，函数既不能安全地放进线程池（内部有 await），
  又不能用同步的方式测试。职责拆开：下载归 func()，像素运算归 make_new_image()。

### 9. 常量提到模块级
_LUMA_RGB / _LUMA_ALPHA 原来可能在函数内构造，现在放模块级只建一次。
- 为什么：numpy 小数组的构造也有开销，循环里每次重建是浪费。

## 四、utils.py（配置持久化）

### 1. save() 改成原子写入
原实现直接打开文件写 JSON。若写到一半进程被 kill / 磁盘满，
customer_api.json 会变成半截的坏文件，**下次启动所有用户的配置全丢**。

现在：先写临时文件，再 os.replace() 原子替换。

    fd, tmp = tempfile.mkstemp(dir=CONFIG_FILE.parent)
    ... 写入并 flush ...
    os.replace(tmp, CONFIG_FILE)

- 为什么：**凡是“覆盖写”重要文件，都应该用临时文件 + 原子改名。**
  os.replace 在同一文件系统内是原子操作，要么是完整的旧文件，
  要么是完整的新文件，永远不会是半截。

### 2. load() 容错
文件不存在、没有读权限、JSON 语法坏了，都返回 {} 而不是抛异常。
- 为什么：**配置文件的损坏不应该阻止程序启动。**
  启动失败 → 用户看到 bot 起不来 → 完全不知道是自己手改配置改坏了。
  返回默认值 + 打一条 warning，程序能跑，问题还能被看见。

### 3. 无参 save() 改成 save(data)
现在必须显式传入要保存的数据。
- 为什么：**显式传参比隐式读取全局状态更安全。**
  看调用处就知道存的是什么，测试时也不用去构造全局状态。

## 五、以后写这个项目时要注意什么（通用清单）

1. **函数返回类型要统一。** 要么永远返回列表，要么永远返回 None + 调用方判空，
   不要“成功给列表、失败给 None”。返回空列表能让调用方少写一个分支。
2. **两个列表按下标对应时，过滤必须成对。**
   zip 之后再过滤，而不是各自过滤之后再 zip。
3. **异步函数里不要放同步的 CPU 重活。**
   用 await asyncio.to_thread(fn, arg)。判断标准：这个操作要几十毫秒以上吗？
4. **网络请求一律带超时和重试**（用 utils/net.py 的 get / aget），
   并且明确区分“重试能解决”（DNS 抖动、连接重置）
   和“重试没意义”（404、401、JSON 解析失败）。
5. **图像/数值计算用 float32。** 除非是累加求和，否则不需要 float64。
6. **numpy 能用整体数组运算就别写逐元素/逐通道循环**，
   广播（[:, :, None]）是省掉循环的主要手段。
7. **写优化前先看中间结果有没有冗余**（三个通道是不是一样？偏移量是不是恒为 0？），
   这类“数学上可省的拷贝”往往比换算法收益更大。
8. **同一份默认值只能定义一次**，其他地方引用常量，别抄字符串。
9. **修改配置和保存配置绑定在一起做**，别让调用方记得手动 save。
10. **删除死代码。** 用搜索确认零引用就删，git 是回收站。
11. **日志打堆栈用 logger.exception**，只在 except 块里用。
    只打 str(e) 在排查时基本等于没打。
12. **给非平凡的步骤写“效果注释”**：不是“这行在做什么”（代码已经说了），
    而是“这段达成什么效果、为什么这样做、不这样做会怎样”。
    这次文件里的注释都是按这个标准写的。
13. **每个 import 都要真的被用到。** 死导入是阅读成本和错误暗示。
14. **中文注释直接写中文**，文件统一 UTF-8。

## 六、这次改动的验证

- python -m py_compile 四个文件全部通过。
- 解析函数：来3张白丝涩图 -> (3, "白丝")；来一份涩图 -> (1, "")；
  来好多张涩图 -> (0, "")；来三张白丝色图 -> (3, "白丝")。
- 真实请求：lolicon(2, "白丝", 0) -> “初号姬为你准备了2张随机白丝色图。”，返回 2 条元数据。
- 合成：600×800 的纯色图 -> 输出 1905×2540 RGBA PNG，48332 字节。
